# ADR 0001：保持单库，用私有组件约束复杂度

- 日期：2026-09-22
- 状态：采用；当产品范围变化时重新评估
- 背景：只有 AES-128、CTR/GCM 两种流模式，主要风险来自重复状态、跨层依赖和输出发布，而非缺少插件或并行引擎。
- 决策：保留单一 `streamcipher::streamcipher` target；参数、模式、GHASH、分派、流适配和文件事务各自有清晰职责。公共头保持小依赖；内部组件不导出为公开头文件。
- 收益：兼容现有字节格式和入口；新增约束可通过消费者、架构规则和回归测试检查；不增加动态注册和后端选择的全局可变状态。
- 代价：GHASH 仍为标量，消息更新循环尚未做多块并行；这影响性能上限，不是宣称已消除的缺陷。

## 有限的文件事务契约

采用同目录暂存、成功后重命名发布。当前要求受信任目录和稳定输入，Windows 目标目录需有正确 ACL。没有句柄相对命名空间防护、跨进程 nonce 分配、崩溃恢复、介质持久化和等长源变更检测保证。

若面向多租户可写目录、服务账户隔离或断电恢复，需要作为独立需求实现平台 I/O 后端、ACL/权限、句柄身份验证和故障注入。不能通过添加几个路径检查把当前 API 描述成拥有这些保证。

## 范围外扩展

AAD/新容器、AES-256、口令 KDF、自动 nonce、并行 GCM、PCLMUL、动态插件分别见 [历史审查台账](../history/architecture-review.zh-CN.md) A111–A120。当前明确不引入；这十项不是已经实现的改进，也不是在当前产品契约下必须补齐的功能。

## 兼容性约束

CTR/GCM 密文字节格式不变。bool 方向工厂保留，Direction 与容量函数为新增入口。删除传递 include 可能要求调用者补上直接使用的模块头；0.x C++ API 不承诺二进制 ABI 稳定，请重新编译消费方。CLI 仍默认 CTR，但文档推荐需要认证时选择 GCM；重复选项现为错误。公共 Vec256 在软件构建中也存在，实现宏不再作为消费方功能检测接口。
